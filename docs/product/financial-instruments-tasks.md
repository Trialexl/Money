# Backlog: финансовые инструменты

Дата: 2026-05-10  
Основание: [PRD: финансовые инструменты](financial-instruments-prd.md)

Приоритет MVP: криптовалюты

## Приоритеты

- `P0` - критично для запуска MVP, без этого модуль нельзя включать.
- `P1` - нужно для полезного первого релиза, но можно выпускать после базового ядра.
- `P2` - улучшение UX, аналитики или автоматизации после MVP.
- `P3` - будущие расширения, включая акции.

## Архитектурные ограничения

- Финансовые инструменты не реализуются в 1С.
- Финансовые инструменты не синхронизируются с 1С.
- Инвестиционные модели не попадают в `OneCSyncOutbox`.
- Текущий учет доходов, расходов, переводов, бюджетов, автоплатежей и 1С sync должен работать независимо от инвестиционного модуля.
- Инвестиционные операции не создают движения денежных кошельков.
- Обычные отчеты доходов/расходов/бюджета не должны меняться от покупки или продажи актива.
- Денежная часть инвестиций ведется существующими документами учета денег, например переводом в скрытый кошелек.
- Зафиксированная прибыль при необходимости отражается вручную текущим документом учета денег, например приходом в скрытый кошелек со статьей `прибыль крипта`.
- Инвестиционный P/L считается только в инвестиционном модуле.

Задачи:

- подключить app в settings;

Acceptance criteria:

- приложение подключено;
- пустой namespace `/api/v1/investment/` не ломает текущие endpoints;
- текущие тесты backend проходят без изменений бизнес-логики.

### P0-BE-006. Изоляция инвестиционных операций от денежных регистров

Цель: покупка/продажа актива не должна автоматически менять текущие кошельки и обычные отчеты.

Задачи:

- не добавлять новый тип инвестиционного документа в `FlowOfFunds`;
- не создавать денежные движения при покупке;
- не создавать денежные движения при продаже;
- не создавать записи в `BudgetIncome` и `BudgetExpense`;
- не создавать `Receipt`, `Expenditure`, `Transfer`;
- проверить, что dashboard-остатки кошельков не меняются от инвестиционной операции;
- явно описать в API/документации, что денежная часть ведется отдельными документами текущего учета.
- явно описать, что прибыль в скрытом кошельке фиксируется ручным приходом, а не автогенерацией.

Acceptance criteria:

- после покупки на 100 000 RUB баланс кошелька не меняется автоматически;
- отчет расходов не меняется от инвестиционной покупки;
- после продажи баланс кошелька не меняется автоматически;
- отчет доходов не меняется от инвестиционной продажи;
- пользователь может отдельно отразить денежную часть переводом в скрытый кошелек;
- пользователь может отдельно отразить прибыль ручным приходом в скрытый кошелек со статьей `прибыль крипта`;
- 1С sync продолжает работать только со старыми типами документов.

### P0-BE-007. Расчет позиции по инструменту

Цель: получить остаток инструмента, себестоимость и среднюю покупку.

Задачи:

- реализовать сервис расчета позиции;
- поддержать покупки;
- поддержать частичные продажи по средневзвешенной себестоимости;
- поддержать корректировки;
- считать `quantity`, `cost_basis_rub`, `average_buy_price_rub`;
- использовать только `Decimal`.

Acceptance criteria:

- несколько покупок пересчитывают среднюю цену;
- частичная продажа уменьшает количество и себестоимость;
- отрицательное количество запрещено;
- расчеты покрыты тестами.

### P0-BE-008. Расчет realized/unrealized P/L

Цель: показывать прибыль/убыток по активам и портфелю.

Задачи:

- фиксировать realized P/L при продаже;
- считать unrealized P/L от текущей цены;
- считать total P/L;
- считать доходность в процентах;
- корректно обрабатывать нулевую себестоимость.

Acceptance criteria:

- realized P/L не меняется при изменении текущего курса;
- unrealized P/L меняется от текущей цены;
- total P/L = realized + unrealized;
- тесты покрывают продажу с прибылью и продажу с убытком.

### P0-BE-009. REST API CRUD

Цель: дать frontend полный контракт MVP.

Задачи:

- endpoints `instruments`;
- endpoints `portfolios`;
- endpoints `accounts`;
- endpoints `operations`;
- фильтры по портфелю, счету, инструменту, типу операции и периоду;
- сортировка операций по дате убыванию;
- OpenAPI schema.

Acceptance criteria:

- frontend может создать и отредактировать все MVP-сущности;
- список операций открывается с новыми операциями сверху;
- API не требует полей 1С;

### P0-BE-010. Тесты независимости текущего учета

Цель: защитить доходы/расходы/бюджет от побочных эффектов инвестиционного модуля.

Задачи:

- тест: покупка актива не меняет расходный бюджет;
- тест: продажа актива не меняет доходный бюджет;
- тест: dashboard кошельков не меняется от инвестиционной операции;
- тест: обычный отчет расходов не меняется от инвестиционной покупки;
- тест: обычный отчет доходов не меняется от инвестиционной продажи;
- тест: 1С outbox не содержит инвестиционные операции.

Acceptance criteria:

- тесты явно фиксируют независимость модулей;
- регрессия в отчетах ловится автоматически.

- короткие подписи дат;
- tooltip с деталями.

Acceptance criteria:

- графики читаемы на desktop и mobile;
- данные совпадают с таблицей позиций.

### P1-FE-102. Отчет по операциям

Статус: готово.

Цель: пользователь видит историю действий с активами.

Задачи:

- фильтры по периоду;
- фильтры по инструменту;
- фильтры по счету;
- итоги внизу;
- экспорт CSV.

Acceptance criteria:

- можно проверить, из каких операций сложилась позиция;
- таблица не смешана с обычными расходами/приходами.

## P1. Ребалансировка

### P1-BE-201. TargetAllocation API

Статус: готово.

Цель: хранить целевые доли.

Задачи:

- CRUD целевых долей;
- сумма целевых долей не должна превышать 100%;
- tolerance percent;
- endpoint получения текущих отклонений.

Acceptance criteria:

- пользователь может задать BTC 50%, ETH 30%, USDT 20%;
- API сообщает, если сумма долей некорректна.

### P1-BE-202. Расчет ребалансировки

Статус: готово.

Цель: показать отклонения от целевой структуры.

Задачи:

- текущая доля;
- целевая доля;
- отклонение в процентах;
- отклонение в RUB;
- примерная сумма buy/sell.

Acceptance criteria:

- если BTC выше цели, система показывает сумму сокращения;
- если ETH ниже цели, система показывает сумму докупки;
- текст не выглядит как инвестиционный совет.

### P1-FE-201. Экран ребалансировки

Статус: готово.

Цель: сделать рекомендации понятными.

Задачи:

- карточки отклонений;
- таблица целевых и текущих долей;
- цветовая индикация выше/ниже цели;
- настройка tolerance.

Acceptance criteria:

- пользователь понимает, что именно выбивается из цели;
- нет автоматического создания операций.

## P2. AI/Telegram

### P2-AI-001. Read-only команды портфеля

Статус: готово.

Цель: бот отвечает на вопросы о портфеле без создания операций.

Задачи:

- intent `get_portfolio_overview`;
- intent `get_instrument_position`;
- intent `get_rebalance_status`;
- компактный Telegram формат;
- не смешивать с командами расходов.

Acceptance criteria:

- `портфель` возвращает стоимость и P/L;
- `сколько btc` возвращает количество, стоимость и P/L;
- ошибки курсов не ломают остальные команды бота.

### P2-AI-002. Создание инвестиционных операций через бот

Цель: бот помогает занести покупку/продажу.

Задачи:

- intent `create_investment_buy`;
- intent `create_investment_sell`;
- LLM получает инструменты, счета и кошельки;
- preview перед созданием;
- финальное подтверждение.

Acceptance criteria:

- `купил btc на 100000 с альфы` не создает документ вслепую;
- бот спрашивает недостающие данные;
- после подтверждения создается инвестиционная операция.

## P3. Акции

### P3-BE-401. Поддержка типа `stock`

Цель: расширить модуль на акции без новой архитектуры.

Задачи:

- включить тип `stock`;
- добавить поля биржи/ISIN при необходимости;
- подключить provider котировок акций;
- учесть валюту бумаги.

Acceptance criteria:

- акция хранится как `Instrument`;
- позиции и P/L считаются тем же сервисом.

### P3-BE-402. Дивиденды

Цель: учитывать доходность акций.

Задачи:

- operation type `dividend`;
- realized income в инвестиционном модуле;
- не создавать денежные движения автоматически;
- если пользователь хочет видеть денежное поступление в кошельках, оно отражается отдельным ручным документом текущего учета денег;
- не смешивать с обычными бытовыми доходами без явного решения.

Acceptance criteria:

- дивиденд увеличивает инвестиционный результат;
- денежный кошелек не меняется автоматически;
- инвестиционный отчет видит дивиденд как доход портфеля.

### P3-BE-403. Split и корпоративные действия

Цель: корректно менять количество бумаг без P/L.

Задачи:

- operation type `split`;
- пересчет количества;
- сохранение себестоимости;
- аудит.

Acceptance criteria:

- split не создает прибыль/убыток;
- средняя цена корректно меняется.
